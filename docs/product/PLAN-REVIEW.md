# Plan Review — adversarial gate on the v2 planning stack

BMAD review gate over `PRD.md`, `ARCHITECTURE-V2.md` and `EPICS.md`. Three independent
reviewers attacked the plan from a distinct lens. **All three returned `sound-with-fixes`**:
the plan is directionally right and must not ship unamended.

| Lens | Verdict | Must-fix |
|---|---|---|
| exhaustiveness | `sound-with-fixes` | 9 |
| deploy-reality | `sound-with-fixes` | 11 |
| invariants | `sound-with-fixes` | 14 |

**Total: 34 must-fix items.** Each is reproduced verbatim below with its rationale and fix.
They are binding: a story that lands without addressing the items touching it is not done.

---

## Release split (decision)

The exhaustiveness reviewer measured the plan at ~139 stories / 13 epics for v2.0 — on the order of a
year of single-engineer work, with Epic 13 gating every release. That is not a release, it is a roadmap.

**Decision — v2.0-core = Epics 1-5** (deployment, self-explaining decisions, independent verification,
supervising the supervisors, one guard pipeline). Epics 6-13 move to v2.1/v2.2. `FR-110`'s console gate
is scoped to the controls the release actually ships, not to everything.

Rationale: Epics 1-5 are exactly the scope-test sentence — an operator can deploy it in one command,
understand every decision it makes, and prove the record independently. That is a defensible product.

## Security invariants — 14 must-fix

> I read PRD.md, ARCHITECTURE-V2.md §§1.4–5, EPICS.md at the referenced stories, and the real core/audit.py, core/db.py, core/risk.py, core/compliance.py, api/security.py, api/audit.py and all 14 shipped migrations.

The plan is better than most. Payload v1 and compute_entry_hash are genuinely left untouched with provenance going to annex columns — that is the right call and it is stated as the whole point. The referential-integrity reasoning in §2.B.1 (no FK on an append-only table, because on-delete cascade or set-null would fire the 0005 triggers and break the parent delete) is correct and non-obvious, and the constraint name it drops, audit_log_gateway_token_id_fkey, is the right auto-generated name for the FK added in 0006. It caught D11 — I confirmed core/compliance.py::oversight_coverage really does query audit_log with no tenant predicate while its caller holds tenant_id. It resolves the erasure-vs-append-only collision in favour of §4.2 rather than fudging it. It refuses the seq column for the right reason and names truncation, annex coverage and the anchor window as residual risks instead of over-claiming. The 0017 TRUNCATE trigger is real: 0005's row triggers genuinely do not fire on TRUNCATE.

What it gets wrong falls into three recurring patterns.

First, invariants asserted in prose and not in artifacts. The §4 rule "RLS enabled in its creating migration" is stated once, then thirteen new tables are specified without a single enable-row-level-security line, and 0016 opts out explicitly. Every one of the 13 tables shipped so far has it. On hosted Supabase that is anon/authenticated exposure through PostgREST, not a stylistic lapse. Same pattern with monotonicity: asserted for annotations only, while eight guards get composed and trust_discount is the one input that moves a verdict down.

Second, the audited party gets to write its own audit. enforcement_mode is an input field on CallContext while AuthorizeRequest is client-supplied; session_id, lineage and ai_system_id likewise. enforcement_mode=mandatory is the strongest claim in the entire Group D thesis, and as specified an SDK client can simply assert it. That is a forged compliance artifact produced by the thing under supervision, and it undermines the transparency plane more than any missing feature would.

Third, features whose schema does not deliver their stated goal. session_taint keyed on (tenant, session_id) with an agent-declared session_id does not survive "one session per task" — its own story says that is the point, and its ACs only test same-session reconnection. The channel approval callback authenticates a link, not a clicker, so a Slack channel becomes a bearer credential for approving irreversible actions. core/control_events.record takes five fields that have no column anywhere in 0016–0028, which will push control-plane strings into Payload v1 columns and unbounded operator notes into a log the plan says is never erased.

The one genuinely absent control is SSRF on tenant-supplied outbound URLs — sinks, notification webhooks and anchor targets all fetch tenant-controlled URLs, and grepping all three documents for SSRF, loopback, link-local or private-range handling returns nothing. The compose topology puts api and worker on a private network with db and GoTrue, which turns this from a common web bug into a pivot into the operator's network, in the deployment mode being sold to buyers whose stated objection is uncontrolled dependencies.

None of these are architectural dead ends. All thirteen are fixable inside the plan's own structure without changing its shape, which is why the verdict is sound-with-fixes rather than not-sound. But items 1, 2, 4, 5 and 6 must land before any code merges: they are cheap now and expensive after 0016–0028 ship, because §V-4 forbids editing a released migration.

### INV-1. RLS is silently dropped on the new tables. The per-table rule in §4 prose says "RLS enabled in its creating migration", but the actual DDL shown for 0016 (`schema_migrations`, explicitly annotated "No RLS"), 0019 (`halts`, `job_runs`), 0020, 0021, 0022, 0023, 0024, 0025, 0026, 0027 and 0028 contains not one `alter table ... enable row level security` statement.

**Why it matters.** Violates invariant 3. I checked every shipped migration: 13 of 13 tables created so far enable RLS in the same file — the codebase holds this perfectly today and the plan regresses it. On hosted Supabase, `alter default privileges in schema public grant all on tables to anon, authenticated` is the project default and PostgREST exposes `public`; a table created without RLS is readable (and, with the default grants, writable) by any authenticated user of the project and often by `anon`. `halts` leaks other tenants' emergency-stop reasons and exposes a resume path, `job_runs.detail jsonb` carries cross-tenant operational detail, `policy_versions.yaml` is every tenant's policy document, `session_taint` and `budgets` are tenant data, and `schema_migrations` is a schema map. This is the single highest-blast-radius item in the plan.

**Fix.** Add `alter table <t> enable row level security;` plus a `<t>_select_own` policy and the two-tenant test to every one of 0019–0028 in the file that creates the table, not in prose. For the two tables with no tenant dimension (`schema_migrations`, `job_runs`), enable RLS with **zero policies** and add `revoke all on <t> from anon, authenticated;` — deny-by-default rather than "readable only by the backend role", which is an assumption about grants, not an enforcement. Extend the existing migration-lint test (§2.A.3 FR-99) with a third assertion: every `create table` in `supabase/migrations/*.sql` is followed by `enable row level security` in the same file, and CI fails otherwise.

### INV-2. `enforcement_mode` is an input field on `CallContext` (ARCHITECTURE-V2.md:541) and `AuthorizeRequest` is client-supplied, so the audited party chooses the label that describes how strongly it was audited. Nothing in FR-3, the §2.C.1 text or EPICS story ACs (EPICS.md:1119-1120 only says which value each path *reports*) forbids reading it from the request body.

**Why it matters.** Violates invariant 1 in its evidential form and poisons the whole Group D thesis. `enforcement_mode=mandatory` is the strongest claim the product makes about an audit entry — it is what C-7 and OQ-3 rest on when the Evidence Pack asserts Article 14 oversight. If an SDK client can POST `enforcement_mode: "mandatory"` to `/v1/authorize`, an agent that never obeys a verdict produces an audit trail and a compliance export indistinguishable from an MCP-gateway-enforced one. That is a forged compliance artifact, generated by the party being supervised.

**Fix.** Remove `enforcement_mode` from `AuthorizeRequest` and from any MCP-side header. `evaluate_call` must not accept it from the caller: derive it inside the ingress adapter — `gateway/server.py` hardcodes `mandatory`, `api/authorize.py`/SDK hardcode `cooperative`, `api/llm_proxy.py` hardcodes `cooperative`, the Inspector replay path hardcodes `evaluate_only`. Construct `CallContext` with `enforcement_mode` set by the adapter, and add a 422 (not a silent ignore) if the field appears in a request body. Add a test that posts `enforcement_mode=mandatory` to `/v1/authorize` and asserts the persisted annex column reads `cooperative`.

### INV-3. Same class of defect, wider: `session_id`, `trace_id`, `lineage` (`parent_request_id`, `delegation_subject`, `originating_principal`, `call_depth`), `ai_system_id` and the FR-4 "agent-declared digest of the preceding tool result" are all written into audit annex columns from values the agent supplies, with no marker distinguishing declared from derived.

**Why it matters.** AT-5 ("every entry answers, without interpretation: which agent, on whose behalf, in which session") is presented as provenance, but for the HTTP/SDK path these are self-reported by the audited principal. An investigator reading an export cannot tell which fields were established by xSOM and which were asserted by the thing under investigation.

**Fix.** Keep only server-derived attribution unqualified: `tenant_id` and `gateway_token_id` come from `resolve_gateway_principal` (api/security.py:179) and nothing else. Wrap every client-supplied field in the `lineage` jsonb under a `declared` sub-object (`lineage.declared.{parent_request_id,...}`) or add a `provenance_source text[]` annex column listing which fields were declared. `docs/AUDIT_FORMAT.md` and the export renderer must display declared fields as declared. `ai_system_id` should be resolved server-side from `gateway_tokens.ai_system_id` (0022 already adds that column) and never accepted from the request.

### INV-4. `session_taint` has `primary key (tenant_id, session_id)` (0023) and `session_id` is agent-declared on the HTTP path (FR-4) and "generated as a last resort" at ingress (FR-56). Story 7.9's stated goal is that "one session per task does not reset it to clean every time", but its AC-3 only tests reconnection **with the same session**.

**Why it matters.** Weakens M12's guarantee. The schema delivers the opposite of the story's premise: an agent that has ingested an injected tool result sheds taint by presenting a fresh `session_id` — or simply by reconnecting, since a newly generated session is resolvable and clean. V-9 ("an unresolvable session on an irreversible action is treated as tainted") does not fire, because the session resolves fine; it is just new. The indirect-prompt-injection guard is bypassed by one string change, at the exact moment (a following irreversible/external_send) it exists to cover.

**Fix.** Add `gateway_token_id uuid` to `session_taint` and record it whenever taint is marked. In the taint guard, an `irreversible` or `external_send` call is escalated if **either** the session is tainted **or** the calling `gateway_token_id` has an unexpired taint row, regardless of `session_id`. Make the agent-scoped window shorter than the session-scoped one if you want to bound the blast radius, but not zero. Add an AC to Story 7.9: given a tainted session, when the agent presents a brand-new `session_id` on the same gateway token within the window, an irreversible action is still escalated.

### INV-5. FR-21 / EPICS Story ~1771: the channel approval callback is authenticated by "an HMAC signature **and** a single-use per-approval nonce" and "resolves to a member identity". The member identity is carried in the payload we signed and sent into the channel.

**Why it matters.** Violates invariant 1. The signed callback URL *is* a bearer credential that approves an irreversible action, and it is delivered into a shared Slack channel or an email that can be forwarded. Anyone who can read the message — a channel member with no xSOM role, an inbox delegate, an SMTP hop — can exercise it, and the audit entry will name the member the link was addressed to. Separation of duties (FR-19) is defeated by the same trick: the requester who can see the channel approves as someone else. "Resolves to a member identity" is assertion, not authentication.

**Fix.** Identity must come from the channel provider's own verified request signature (Slack's signing secret over the raw body, giving the *clicking* user's id; equivalent for Teams), mapped to a `memberships` row; our HMAC + nonce protects payload integrity and replay only, and must never be sufficient on its own. Reject the callback if the provider-verified clicker maps to no member of the tenant, or maps to `requested_by`. Gate the whole channel path behind a per-tenant opt-in that is **off by default for `irreversible`** — for that class, the callback returns a deep link to the console instead of deciding. Fold this into OQ-11's resolution before the story is implemented, not after.

### INV-6. `core/control_events.py::record(conn, *, tenant_id, actor, event, object_ref, before_digest, after_digest, note)` (ARCHITECTURE-V2.md:414) has nowhere to store `event`, `object_ref`, `before_digest`, `after_digest` or `note`. Migration 0017 adds seventeen annex columns and none of them is any of these; I grepped 0016–0028 and they do not exist.

**Why it matters.** Two consequences, both bad. First, the implementer will overload existing Payload v1 columns — `tool_name` for `event`, `error` or `args_hash` for the digests — which directly undoes FR-114 ("error means error") in the same release that introduces it, and puts control-plane strings into the chain-protected payload where they can never be corrected. Second, `note` is unbounded operator free text heading into `audit_log`, which §2.B.5 declares is never erased under any circumstance: that is a permanent, un-erasable PII sink, colliding with invariant 10 and with FR-135's own erasure position.

**Fix.** Add to 0017: `control_event text`, `object_ref text`, `before_digest text`, `after_digest text`. Do not add `note` to `audit_log` at all — store operator notes on the mutable object row (as 0021 already does for `approvals.decision_reason_text`) and reference them from the entry by digest only, exactly as the policy-YAML rule already does. Bound `object_ref` and `control_event` to a validated vocabulary, and extend `scripts/audit_security.py` to fail if any control-plane write passes a value longer than N or matching a secret shape (the plan already promises this check — give it a column to check).

### INV-7. `event_sinks.endpoint`, `notification_channels.target` (kind=webhook) and the §2.B.2 Layer-4 `webhook` anchor target are tenant-supplied URLs that the backend fetches with `httpx`. Grepping PRD.md, ARCHITECTURE-V2.md and EPICS.md for SSRF, loopback, link-local, 169.254 or private-range controls returns nothing.

**Why it matters.** Server-side request forgery from the control plane, and the compose topology makes it worse rather than better: in §2.A.1 the `api` and `worker` containers sit on a private network with `db`, `auth` (GoTrue, which exposes an admin API) and each other. A tenant admin registering a sink at `http://auth:9999/...` or `http://169.254.169.254/latest/meta-data/iam/...` turns a supervision feature into a pivot into the operator's network, and the egress payload plus HMAC signature give an oracle for the responses. This also punches a hole in the self-host story you are selling to platform engineers whose whole objection is "do not introduce an uncontrolled dependency".

**Fix.** One shared outbound-request helper for sinks, notifications and anchors: scheme must be `https` (allow `http` only when `ENV != prod` and the host is explicitly allowlisted), resolve the hostname first and reject any address in loopback / link-local / RFC1918 / RFC6598 / IPv6 ULA / `::1`, connect to the resolved address with the Host header pinned so DNS rebinding cannot re-point it, disable redirect following, cap response size and timeout, and never return the response body to the tenant. Add an operator-level `EGRESS_ALLOWED_HOSTS` for locked-down deployments. Test the deny-list with a sink pointed at `127.0.0.1` and at `169.254.169.254`.

### INV-8. §2.C.7 / 0021 grants `memberships` INSERT/UPDATE/DELETE to `authenticated` with the policy shown only for insert (`memberships_admin_insert ... with check (...)`); update and delete are hand-waved as "plus matching update/delete policies, and grants".

**Why it matters.** Two distinct defects. (a) An UPDATE policy with only a `using` clause and no `with check` lets a tenant admin `update memberships set tenant_id = '<victim>'` — the row moves into another tenant, and since `core/signup.py:101` is the only writer today, memberships is the table any future tenant-resolution or invite flow will trust. That is cross-tenant escalation through the very policy added to enforce isolation. (b) More structurally: granting direct write access to `authenticated` means an admin holding the anon key and their own JWT can mutate memberships through PostgREST, bypassing `api/members.py` entirely — so the mutation happens with **no control-plane event**, defeating FR-38 ("attribution is mandatory") and SM-4's coverage gate, which only enumerates FastAPI routes.

**Fix.** Every UPDATE policy in 0021 gets both `using (...)` and `with check (...)` carrying the tenant predicate **and** the admin role predicate, so a row can neither be read into nor written out of a foreign tenant. Then reconsider (b): keep the write policies as defence in depth but do **not** `grant insert/update/delete on memberships to authenticated` — let writes go through the API on `service_role`, which is the only path that can write the control-plane event in the same transaction. If direct console writes are genuinely required, add a matching trigger on `memberships` that refuses any write not accompanied by a control-plane event in the same transaction. Story 4.10 AC-2 should assert the non-admin is refused **and** that an admin's direct-SQL write is refused too.

### INV-9. §2.C.2: "Fail-closed (FR-25): if halt state cannot be read, `irreversible` and `external_send` are denied." Everything else — `write`, `sensitive`, unclassified — proceeds.

**Why it matters.** Violates invariant 4 in spirit and defeats the feature's own purpose. An emergency stop is invoked precisely during an incident, which is precisely when the database is degraded. A tenant-scope halt that still lets an agent perform `write` actions because the halts table is unreadable is not an emergency stop. It is also inconsistent with the rest of the plan: the same failure mode denies nothing at all for a tool the operator has just halted by name.

**Fix.** On a halt-read failure the pipeline denies every class except `read`, with `decision_reason=halt` and `outcome_status=not_executed`. If that is judged too aggressive for the reversible classes, make it a per-tenant setting whose default is deny-all-but-read and whose relaxed value is refused when `ENV=prod` — never the reverse. Add the AC: given the halts query raises, when a `write` call arrives, then it is denied and an entry is written.

### INV-10. §2.A.3 baseline adoption: on a database that has `audit_log` but no ledger, `core/migrate.py` records 0001–0015 as applied without running them, "detected by probing for a sentinel object per file group".

**Why it matters.** A coarse, group-level probe on a partially-migrated database marks migrations as applied that never ran, and the objects those files create are RLS policies and the `audit_log` append-only triggers. A deployment that stopped after 0009 gets 0010–0015 stamped as applied; `dlp_config`, `tool_fingerprints` and their RLS policies never exist, `/health/ready` reports the head matches, and the stack declares itself healthy with tenant isolation missing on tables the code will then create implicitly or fail on. It is a fail-open that produces a green boot gate.

**Fix.** Probe per file, not per group, with one sentinel object per migration, and require **all fifteen** to be present before adopting the baseline. If the probe result is mixed, refuse to start and exit non-zero with the list of which files look applied and which do not — do not guess. Put adoption behind an explicit `xsom migrate --adopt-baseline` that prints exactly what it will assume and requires confirmation, so it can never happen as a side effect of `docker compose up`. Add a test that runs the adopter against a database migrated only to 0009 and asserts it refuses.

### INV-11. `GET /health/ready` is unauthenticated and returns the `capabilities` map (`signup`, `judge`, `dlp`, `egress`, `anchors`, `worker_fresh`) plus the schema head (EPICS AC-3). `GET /v1/data/manifest` has no stated authentication anywhere in FR-133 or Story 11.8, and its inventory is generated from `information_schema.columns`.

**Why it matters.** `/health/ready` is a security-posture disclosure endpoint: an unauthenticated attacker learns that DLP is off, anchors are unconfigured and the worker is stale — that is a target-selection oracle, and "no secrets in the response" (AC-4) does not address it. The manifest, if unauthenticated, publishes the full column inventory of every table; if it queries `information_schema` per request it is also an unauthenticated query amplifier, and the 5-second memoisation promised for `/health/ready` is not promised for it.

**Fix.** Split readiness: unauthenticated `/health/ready` returns `{ok: bool}` and the three boot-gate booleans only (that is all a load balancer and a compose healthcheck need); move the `capabilities` map to an authenticated `GET /v1/system/capabilities` behind `require_role`. For the manifest, generate it at build time into `docs/DATA_MANIFEST.md` plus a checked-in JSON artifact, serve that artifact from `GET /v1/data/manifest` behind `get_current_user`, and never touch `information_schema` in a request handler — `tests/test_data_manifest.py` is where the live schema is compared against the artifact.

### INV-12. §2.B.2 Layer 3 ships `LocalKeySigner` as the self-host default with the checkpoint signing key "generated by `xsom init`", and defers custody to OQ-9. Layer 4 anchoring is described as "not optional for a customer who cares" but is off by default and has no prod gate.

**Why it matters.** A checkpoint signed with a key that lives wherever `xsom init` put it, verified against a public key published from the same database it attests, is a witness the attacker controls. Anyone who can UPDATE `audit_log` (the threat model the plan itself names in FR-125) can, in the default single-host compose deployment, also read the signing key from disk and re-sign a consistent checkpoint set. The default configuration therefore delivers the *appearance* of independent verification, which is worse than not shipping it — and the honest-limits paragraph in `docs/SECURITY.md` corrects the old over-claim while creating a new one.

**Fix.** Three concrete constraints, decided now rather than deferred to OQ-9. (1) The private key is never stored in Postgres and never in a column of any table — file with mode 0600 or KMS only, and `scripts/audit_security.py` gets a check that fails if a private key material pattern appears in any migration or seed. (2) `xsom doctor` and the authenticated capabilities endpoint report `checkpoints: self_witnessed` whenever the signer key is on the same host as the database, and the console and every Evidence Pack render that phrase verbatim next to the checkpoint section. (3) When `ENV=prod`, at least one enabled `AnchorTarget` is required for `/v1/audit/verify` to report `anchors.configured=true`, and the Evidence Pack must not present checkpoint verification as independent evidence when it is false.

### INV-13. The plan asserts monotonicity in exactly one place — annotations ("monotone-upward only", ARCHITECTURE-V2.md:644, EPICS.md:1960) — while `core/pipeline.py` composes eight guards and `core/risk.py:143` contains the one input that moves a verdict *down* (`score = max(0, score - trust_discount(clean_streak))`). The stated regression guard is a golden-decision corpus asserting the refactor changes no verdict for existing policies.

**Why it matters.** A golden corpus proves today's inputs produce today's outputs; it says nothing about a future guard or a future band configuration relaxing a verdict, which is precisely what invariant 1 forbids and what an eight-guard pipeline makes easy to do by accident. `escalate_by_risk` is careful today (it only scores an `auto` base and returns `tier if _ORDER[tier] > _ORDER[base] else base`, with the `irreversible` floor in `band`) — but that discipline lives inside one function, and the refactor moves the composition somewhere else. `external_send` has no floor at all.

**Fix.** Make it a structural property of the pipeline rather than a convention: `evaluate_call` folds guard results through a `max` over `_ORDER` and the guard interface returns a *minimum* tier, so a guard is incapable of lowering a prior guard's verdict. Add a Hypothesis-style property test over the whole pipeline: for any `CallContext` and any sequence of guard outcomes, the final `Approval` is >= every intermediate one, and for `action_class in (irreversible, external_send)` the final verdict is never `auto` or `notify` regardless of trust streak, risk band configuration or `enforcement_mode`. That test, not the golden corpus, is the invariant-1 gate.

### INV-14. Layer 2's standalone verifier (`tools/xsom_verify.py`, stdlib only) must rebuild the canonical payload byte-for-byte, but the payload's `ts` field is produced by `core/audit.py:101` as `ts.astimezone(UTC).isoformat()` on a psycopg `datetime`, and the export path serialises through `core/audit.py:235` (`r[1].astimezone(UTC).isoformat()`). Neither `docs/AUDIT_FORMAT.md` nor the plan pins that string format.

**Why it matters.** `isoformat()` emits microseconds only when non-zero and `+00:00` rather than `Z`. Any JSON re-serialisation in the export pipeline that normalises to `Z`, drops sub-second precision, or round-trips through a Pydantic `datetime` field silently changes the byte string that goes into `sha256(prev_hash + payload)`. The standalone verifier then reports FAIL on an intact chain — or, worse, the corpus test passes because both implementations share the same generated fixtures while real exports fail. The flagship "independently checkable" claim turns into a support burden that erodes trust in the audit rather than establishing it.

**Fix.** Pin the canonical `ts` representation in `docs/AUDIT_FORMAT.md` as the exact output of `datetime.astimezone(UTC).isoformat()` with its variable-microsecond behaviour spelled out, and have the export emit `ts` as that raw string (never as a Pydantic `datetime` that re-serialises). Add a CI test that takes a real `GET /v1/audit/export` response — not a generated fixture — through `tools/xsom_verify.py` and asserts OK, including at least one entry whose timestamp has zero microseconds and one that does not.


## Deployment reality — 11 must-fix

> I attacked this expecting hand-waving and largely did not find it. The diagnosis is real and honest: I independently reproduced D10 — `Settings(_env_file='.env.example')` raises `SettingsError` on `cors_allow_origins`, so the documented quickstart genuinely does not boot, and `tests/test_config.py` is structurally blind to it exactly as claimed. D9 checks out too: `.dockerignore` excludes `supabase` and `scripts`, so the image provably cannot migrate itself. The migration-ledger design with sentinel-probed baseline adoption is the right shape, the `tests/test_rls.py`-unmodified-against-compose invariant is precisely the right gate for R-12, and Story 1.24's validation-by-deliberate-defect-reintroduction (A-12) is genuine engineering discipline that most plans in this position skip. The strategic calls — GoTrue over writing an identity provider (AD-5), one Postgres dialect with no SQLite path (AD-8) — are correct and well argued.

But the deployment plane fails on the third that matters most: identity. "Ultra facile de déploiement" rests entirely on the `auth` service, and that service has no story, no ACs, no effort estimate, and three prose lines of design. Simulating the stranger's run, the first command dies before the console ever renders: the keypair GoTrue needs at boot is generated by a CLI the plan schedules AFTER boot; `core/config.py`, `core/signup.py` and `@supabase/ssr` all hard-code a `/auth/v1` prefix that is a Kong artifact absent from a six-service compose file with no proxy; and the anon and service keys that the console and `xsom init` both hard-require are minted by nothing. Any one of those three is a hard stop at minute one. Below them sit softer but real failures — an issuer URL baked into the CI-built console image by `NEXT_PUBLIC_` inlining (defeating FR-89, a stated security requirement), a `BYPASSRLS` grant managed Postgres will refuse, two competing bootstrap paths with no stated login credential, unbudgeted cold-cache build time on an unvalidated architecture, unparameterised ports, and no backup story for the hash chain the whole product sells.

None of these are architectural dead ends and none require abandoning the approach — they are missing specification concentrated in one under-planned area, which is why this is sound-with-fixes rather than not-sound. The honest scope statement is narrower than the current text: v2 can credibly promise "one command plus one bootstrap command, on Docker, with a bundled identity service that speaks the GoTrue protocol, on amd64 and arm64." It cannot yet promise "any OIDC issuer by configuration alone" — the `auth.users` FK in `0001_init_tenancy.sql` and the `app_metadata.tenant_id` RLS predicate in all fifteen migrations forbid it. And it should not publish the ≤10-minute SM-1 median until a cold-cache first run has actually been measured on an ARM laptop rather than inferred from a warm x86 CI runner. Fix the eleven items above — items 1 through 4 decide whether the promise survives first contact — and the claim becomes defensible.

### DEP-1. The GoTrue `auth` service — the single riskiest new component — has no owning story, no acceptance criteria, and no configuration design.

**Why it matters.** Epic 1 has 26 stories. Story 1.13 (compose, Effort L) lists files `docker-compose.yml, Makefile, deploy/, docs/DEPLOY.md, README.md` and Story 1.11 covers only `deploy/auth_compat.sql`. Grep across EPICS.md returns ZERO occurrences of "GoTrue", "supabase/auth", "GOTRUE_", "keypair" or "RSA". The entire identity design lives in three prose lines at ARCHITECTURE-V2.md:195-206. Nothing specifies the image pin, GoTrue's own DB user and schema ownership, `GOTRUE_JWT_*` / `GOTRUE_SITE_URL` / `GOTRUE_URI_ALLOW_LIST`, mailer behaviour, or migration ordering against `auth_compat.sql`. R-6 is rated Med·High and its only mitigation is `AUTH_ISSUER_MODE=selfhost_shared_secret`, which Story 1.10 AC4 REFUSES under `ENV=prod` — so if R-6 fires, self-host in production is impossible and FR-85 silently degrades to a dev-only toy. An unestimated Med·High risk carrying the whole of Group C is not a plan, it is a hope.

**Fix.** Split a dedicated story: "The identity service is a pinned, configured, tested container." Pin an exact `supabase/auth` tag; spike its asymmetric-signing support (`GOTRUE_JWT_KEYS`) BEFORE committing FR-85 to MVP; write ACs for its DB role, its migration ordering vs `auth_compat.sql`, its JWKS endpoint and its offline (no-SMTP) behaviour. Give it an effort estimate. If the spike fails, re-scope FR-85 honestly rather than shipping a prod-refused degraded mode.

### DEP-2. Chicken-and-egg: `xsom init` cannot both run after `docker compose up --wait` and be the thing that configures GoTrue's signing keys.

**Why it matters.** ARCHITECTURE-V2.md:202-203 says "`xsom init` generates an RSA keypair, configures GoTrue with the private JWK set and the compose stack with the public JWKS URL." But UJ-1 (PRD.md:79) and Story 1.24 AC1 both order it `docker compose up -d --wait` → assert `/health/ready` 200 → `xsom init`. Story 1.14 AC2 makes `/health/ready` return 503 unless "the JWKS issuer resolves" — GoTrue must already be running WITH keys before init runs. Container environment is fixed at container start; you cannot inject a JWK set into an already-booted GoTrue. So the keypair must exist before `docker compose up`, and the `xsom` CLI is a Python console entry point (`[project.scripts]`) inside the API image — running it pre-compose reintroduces exactly the Python 3.12 + uv host prerequisite the plan claims to eliminate. Compounding this: EPICS.md, ARCHITECTURE-V2.md and PRD.md contain zero occurrences of `docker compose run` or `docker compose exec`, so how a Docker-only stranger invokes `xsom` at all is never stated, while FR-106 / Story 1.25 promises "the demonstration needs only Docker".

**Fix.** Decide and write down one of: (a) a `deploy/entrypoint.sh` on the `auth` service that generates the keypair into a shared volume on first boot, making compose genuinely self-contained; or (b) an explicit two-step `make up` that runs key generation in a throwaway container first. Then state the CLI invocation surface everywhere it appears (`docker compose run --rm api xsom init …` or a `make init` wrapper) and fix UJ-1's narration to match. "One command" that is actually two is fine — silently three is not.

### DEP-3. The `/auth/v1` path prefix is a Supabase-platform (Kong) artifact, not GoTrue's. Bare GoTrue serves those routes at the root, and the compose topology has no reverse proxy.

**Why it matters.** Three independent call sites hard-code the prefix: `core/config.py::jwks_url` derives `{supabase_url}/auth/v1/.well-known/jwks.json`; `core/signup.py::SupabaseAuthAdmin.__init__` builds `{base_url}/auth/v1/admin/users`; and `@supabase/ssr` in `frontend/lib/supabaseServer.ts` and `frontend/middleware.ts` appends `/auth/v1` internally. The §2.A.1 table lists six services (`db`, `auth`, `migrate`, `api`, `worker`, `web`) — none is a gateway. The claim at ARCHITECTURE-V2.md:191 that "GoTrue *is* that protocol" is true of the payloads and false of the routing. Result: JWKS resolution 404s (so `/health/ready` never goes green), console login 404s, and `xsom init` → `provision_account` → admin API 404s. All three of the promise's load-bearing paths.

**Fix.** Either add a pinned reverse-proxy service to compose that maps `/auth/v1/*` → GoTrue `/*` (and put it in Story 1.13's file list), or make the prefix configurable at all three call sites and prove it. Add an AC asserting the JWKS URL and the admin-user URL actually resolve against the composed identity service — not against a mock.

### DEP-4. The anon key and the auth service key have no specified origin under the plan's asymmetric-signing design.

**Why it matters.** `frontend/lib/config.ts:3` reads `NEXT_PUBLIC_SUPABASE_ANON_KEY` and passes it to `createServerClient` (supabase-js rejects an empty key), and `core/signup.py::build_auth_admin` returns `None` without `supabase_service_role_key` — which disables `xsom init`'s entire zero-SQL bootstrap, since Story 1.15 AC2 depends on `provision_account`. On the hosted platform both are HS256 JWTs signed with the project JWT secret. §2.A.4 renames the variable to `AUTH_SERVICE_KEY` and Story 1.2 AC3 documents it, but nothing anywhere MINTS it. Story 1.15's file list (`cli/main.py, cli/init.py, pyproject.toml, core/signup.py, core/tenant_tokens.py, core/policy_store.py`) contains no key-minting work.

**Fix.** Add explicit ACs to the identity story: `xsom init` (or the first-boot entrypoint) mints the anon and service keys, writes them to `.env` at 0600, and passes the service key only to `api`/`worker`/`migrate` (§4.6). If the pinned GoTrue build requires a symmetric secret for API-key auth even under asymmetric session signing, say so — that materially changes the `.env` surface and the threat model.

### DEP-5. `NEXT_PUBLIC_*` is inlined by Next.js at BUILD time, so a CI-built console image bakes the issuer URL — the exact thing FR-89 exists to prevent.

**Why it matters.** Story 1.12 AC3 requires the frontend image to be built in CI; AC4 says "the image environment receives only `NEXT_PUBLIC_*` values and `CONTROL_API_URL`", and §2.A.6 adds `NEXT_PUBLIC_XSOM_API_URL`. Next 14 statically substitutes `process.env.NEXT_PUBLIC_*` at build; setting it at runtime is a no-op. So the CI-built artifact ships with whatever URL CI had, and FR-89 ("no vendor hostname in any rendered artifact" — explicitly called a security requirement because it routes customer provider keys through someone else's server) is defeated by the packaging, not by the code. The Playwright assertion in §2.A.6 would pass in CI while the shipped image stays wrong.

**Fix.** Cheap fix, but it must be written down: all three consumers (`lib/config.ts:2-3,5`, `lib/supabaseServer.ts`, `middleware.ts`) are server-side only — route handlers and middleware — so drop the `NEXT_PUBLIC_` prefix entirely and read them at runtime. Add an AC that a single prebuilt console image is re-pointed at a different issuer and API origin by environment alone, with no rebuild.

### DEP-6. "Keycloak/Entra/Okta work by configuration alone" (ARCHITECTURE-V2.md:197) is false — the schema and the provisioning path are hard-coupled to a GoTrue-managed `auth` schema.

**Why it matters.** `supabase/migrations/0001_init_tenancy.sql` declares `memberships.user_id uuid not null references auth.users (id) on delete cascade`. Every RLS policy across all 15 migrations reads `auth.jwt() -> 'app_metadata' ->> 'tenant_id'`. `core/signup.py` speaks only the GoTrue Admin REST API. An external IdP populates no `auth.users` row (so every membership insert violates the FK), emits no `app_metadata.tenant_id` claim (so every `*_select_own` policy returns zero rows), and exposes no compatible admin-user endpoint (so `provision_account` cannot run). Story 1.10's ACs cover only JWKS signature verification — the easy 20% — and never touch claim mapping, user materialisation or the FK. Shipping FR-87 as written sells an integration that does not exist.

**Fix.** Scope FR-87 honestly to "any issuer that presents GoTrue-shaped claims", i.e. hosted Supabase or self-hosted GoTrue. Move true external-IdP federation to roadmap and say so in PRD §6.2. If it must stay in v2, add the missing work explicitly: a claim-mapping layer, a local user-materialisation path, and dropping or relaxing the `auth.users` FK — that is a migration and an RLS rewrite, not a configuration change.

### DEP-7. `xsom migrate --and-compat` cannot run against managed Postgres, contradicting Story 1.13 AC4.

**Why it matters.** Story 1.11 AC1 makes `service_role` carrying `BYPASSRLS` load-bearing (it is the stated mitigation for R-12, rated Very High impact), and `core/db.py` documents that the backend "connects with a role that bypasses RLS". Granting `BYPASSRLS` requires an actual superuser; RDS, Cloud SQL and Azure Flexible Server hand out `rds_superuser`-class roles that cannot. Yet Story 1.13 AC4 asserts "Given `DATABASE_URL` is overridden to a managed Postgres … everything else works unchanged", and §2.A.1 names RDS and Cloud SQL explicitly. This path is asserted, not tested — the deploy-smoke workflow (Story 1.24) only exercises the bundled `db` service.

**Fix.** Split the compat layer: the parts any owner role can apply (`auth` schema, `auth.jwt()/uid()/role()`, `anon`/`authenticated`) from the part needing superuser (`service_role` with `BYPASSRLS`). Document the latter as a named DBA prerequisite per managed provider, have `xsom doctor` detect and report it with concrete remediation, and either add a managed-Postgres job to CI or downgrade AC4 from a claim to an explicit untested caveat.

### DEP-8. The "seeded demo tenant" and `xsom init` are two competing bootstrap paths, and neither produces a console credential the operator can log in with.

**Why it matters.** FR-85 and UJ-1 (PRD.md:79) promise `docker compose up` yields "a seeded demo tenant"; Story 1.15 has `xsom init` create the tenant, the admin member and the identity claim. Story 1.13 AC5 mentions the seed only to say it refuses under `ENV=prod`. Nothing states which tenant the console shows, what the demo admin's email and password are, where they are printed, or what happens when `xsom init` runs on an already-seeded database. UJ-1's "eight minutes from `git clone`" includes a console login whose credential is specified nowhere — and SM-1 is measured on exactly that wall clock.

**Fix.** Pick one bootstrap path and delete the other from the narrative. If the seed stays, give it ACs: fixed demo email, generated password printed exactly once, clearly labelled demo tenant, and defined behaviour when `xsom init` runs against an already-seeded database (refuse, or create a second tenant — explicitly, either way).

### DEP-9. Build time, image distribution and CPU architecture are unaddressed, so SM-1's ten-minute target is unbudgeted and the smoke workflow will not measure it.

**Why it matters.** §2.A.1 declares `api`/`worker`/`migrate` as `build: .` and `web` as `build: ./frontend`. A stranger's first `docker compose up` therefore runs `uv sync --frozen` over the full lockfile AND `npm ci` + `next build` on a cold cache, plus pulls `postgres:16-alpine` and `supabase/auth`. No story publishes prebuilt images to a registry. `linux/arm64` appears nowhere in PRD, ARCHITECTURE-V2 or EPICS — and Apple Silicon is the modal evaluator laptop; `supabase/auth`'s arm64 support is an unvalidated assumption sitting directly on the critical path. Story 1.24's smoke runs on a warm x86 GitHub runner, so the "machine floor" cited for SM-1 measures something the stranger will never experience.

**Fix.** Add a story that publishes multi-arch (`linux/amd64,linux/arm64`) images for `api` and `web` to a public registry, and make the shipped `docker-compose.yml` default to `image:` with `build:` as an opt-in override. Add an explicit arm64 assertion. Measure a cold-cache first run on both architectures and reconcile it with SM-1's ≤10 min median before that number is published.

### DEP-10. Host port collisions are unhandled — the most common single cause of a failed first run appears nowhere in the plan.

**Why it matters.** §2.A.1 says all services bind to `127.0.0.1` by default, which is correct and good, but no story fixes or parameterises the host ports. The target persona is a platform engineer, who very often already has Postgres on 5432, something on 3000 and something on 8000. `docker compose up` then fails on bind before anything else in the plan gets a chance to run, and the error points at Docker rather than at xSOM.

**Fix.** Parameterise every published port in `docker-compose.yml` (`${XSOM_DB_PORT:-5432}`, `${XSOM_WEB_PORT:-3000}`, `${XSOM_API_PORT:-8000}`), document them in `.env.example`, and add an AC to Story 1.13. Have `xsom doctor` name a port conflict explicitly as a diagnosable failure with a remediation line.

### DEP-11. No backup, restore or key-custody story for the evidence plane — the one thing self-host is selling.

**Why it matters.** The compose volume `xsom-db` holds the hash chain, and `xsom init` generates the checkpoint signing key locally with custody deferred to OQ-9. On the hosted three-vendor path Supabase handled durability; on self-host nobody does. If the operator loses or regenerates `.env`, every previously signed checkpoint and every external anchor becomes unverifiable — destroying exactly the guarantee UJ-7 ("her opinion does not rest on the vendor's good faith") and FR-121 exist to provide. Grep across all three planning documents returns nothing for backup or restore; OP-10 covers offline operation, nothing covers durability.

**Fix.** Add a story: a documented backup/restore procedure covering the database volume AND the signing key as one inseparable unit, with a restore drill in CI (restore a snapshot, run `xsom verify-chain`, assert green). Have `xsom doctor` detect a signing key that does not match the `key_id` on existing checkpoints and fail loudly rather than silently signing a fresh, unverifiable branch. Resolve OQ-9 before release, not after.


## Exhaustiveness & positioning — 9 must-fix

> This is an unusually strong pair of documents — considerably better than the median PRD I would review. The traceability discipline is real (152 FRs, every one mapped to at least one of 163 stories, testable Consequences on each), the invariant handling is genuinely rigorous (the Invariant collision / Resolution pattern resolves erasure-vs-append-only, framework-owned HITL, and argument storage correctly and in favour of the invariant every time), the honesty is a competitive asset rather than a liability (AT-4 publishing what the chain does *not* detect, FR-51 labelling cooperative enforcement as weaker, FR-144's not-covered rows), and the counter-metrics section is the best part of the document — CM-1 and CM-2 name the two ways this product fails in production and most vendors never write them down. Epic 1 as both first delivery and permanent CI gate is the right call. My attempt to find "you forgot licensing / pricing / residency / threat model / anchor custody" failed: OQ-1, OQ-12, DG-8, FR-126 and OQ-9 all already own them. Credit where due.

The findings above are therefore not "you missed the obvious." They fall into three groups.

First, three genuine holes in the *enforcement core itself* — the part the documents assume is already right and mostly leave alone. The policy engine cannot express a condition on an argument value, unrecognised constraint keys silently fail open (verified in `core/policy.py:252`, against a Glossary in the PRD that asserts four constraint types where the code implements one, and a shipped SPEC example containing two that do nothing), and generic executor tools like `bash`/`run_python` — the highest-blast-radius tools in any real stack — are routed to the LLM judge, which collides with the plan's own NFR-1. A buyer writing their first real policy hits all three inside an hour. These are the concrete answer to "what does a buyer notice on day one."

Second, the missing monitor mode. This is the one I would fight hardest for. The plan ships deny-by-default with no on-ramp, and its own two most important counter-metrics describe precisely what happens when you do that. It is also cheap — one branch at the decision boundary — and the promotion report it enables ("enforcing today would have held 43 calls") is probably the single best sales artifact the product could have.

Third, scope and positioning. 139 stories with no cut line and Epic 13 gating the release is a waterfall; the scope-test sentence in §6 is satisfied by roughly the first five epics and should be the GA boundary. And on positioning: the plan is right that the intersection is the differentiator, but it never confronts that the human-approval leg is being commoditised by the frameworks and the identity vendors, that Epic 8's adapters concede this by routing those hooks to xSOM, or that FR-51's honest `cooperative` label makes the concession visible to buyers at evaluation time. There is no named-competitor analysis anywhere. The cuts I propose — cost-accounting precision, four of five framework mappings, the LLM proxy as an ingress path — are all places the plan drifts into territory where it competes on someone else's terms with a free incumbent.

Verdict is sound-with-fixes rather than not-sound: the thesis, the architecture, the invariant discipline and the sequencing are correct, and none of the nine findings requires rethinking the product. Fix the enforcement-core holes, add monitor mode, cut the commodity surface, and define a shippable release boundary.

### EXH-1. No observe-only / monitor enforcement mode anywhere in the plan. `Enforcement Mode` has exactly two values (mandatory | cooperative — PRD §3, Story 5.3 AC-2). Grep for shadow / monitor / observe-only / audit-only across PRD.md and EPICS.md returns zero hits.

**Why it matters.** This is the single largest adoption blocker in the plan and it contradicts the plan's own risk model. FR-107 ships `unknown_tool: deny` as the day-one default. For a prospect with an existing agent fleet that means every unlisted tool breaks on the first call. The PRD narrates this as acceptable in UJ-2: Sofia 'runs her integration suite' and discovers four tools are denied. No platform team turns deny-by-default on a production fleet and finds out what breaks by breaking it. NFR-7 and G-S5 explicitly protect *existing* tenants from silently tightened enforcement — but offer a *new* tenant no equivalent on-ramp, which is precisely the population the whole release is built to win (SM-1, UJ-1). CM-1 (auto-tier widening) and CM-5 (bypass rate) are named as the two most damaging failure modes, and the plan ships no mechanism to avoid them other than hoping the first policy is right. FR-11 (simulate a candidate policy over past audit entries) and FR-60 (single-call evaluate-only replay) are both retrospective/point tools; neither lets a fleet run live under the full pipeline without blocking. Every comparable security control (WAF, CSP, DLP, Falco) ships report-only first, and every competitor gateway will offer it.

**Fix.** Add a third Enforcement Mode value, `monitor`, as MVP scope in Group A / Epic 5, scoped per Tenant and per Agent. In monitor mode the full Guard Pipeline runs and writes a complete Audit Entry with the decision it *would* have made, and the call proceeds. Constrain it so it does not erode CLAUDE.md §4.1: explicitly opt-in per agent, time-boxed with a mandatory expiry, enabling/extending it is a Control-Plane Event (FR-36), `enforcement_mode=monitor` is stamped on every entry and rendered everywhere cooperative is, and monitor entries are excluded from Evidence Packs as oversight evidence exactly as C-7 handles cooperative. Add the promotion surface that makes it valuable: 'if you enforced today, these 43 calls in the last 7 days would have been held and these 6 denied, on these tools' — which is also the highest-converting artifact in the product. Add a counter-metric for tenants that never leave monitor. Cost is low: the pipeline already computes the verdict; this is one branch at the decision boundary plus an annex value.

### EXH-2. Unrecognised policy constraint keys silently fail OPEN. `core/policy.py:252 _constraints_ok` reads exactly one key, `allowed_domains`, and returns `True` for everything else. `docs/SPEC.md:193-197` ships an example policy containing `dry_run: true` and `business_hours_only: true`; neither is enforced anywhere. PRD §3 Glossary asserts the opposite — 'Constraint — a bounded condition on a policy Rule (allowed domains, allowed clients, dry-run required, business hours). Violation fails closed.' No FR in the 152 and no story in the 163 mentions this.

**Why it matters.** An operator who writes `business_hours_only: true` gets a control that reads as enforced in the policy YAML, is documented as enforced in the shipped SPEC, and is defined as enforced in the v2 Glossary — and does nothing. That is a silent fail-open in the one subsystem whose entire discipline is fail-closed: unknown *tools* deny (FR-107), unknown *constraints* allow. A typo (`allowed_domain`, `allowedDomains`) also silently disables the one constraint that does work. It is a live defect today, and worse for v2 because the plan hard-codes the false claim into the Glossary and then builds a 'single guard pipeline' (Epic 5) that relocates `_constraints_ok` without noticing it. It also directly undermines FR-113 (every decision self-explaining) and SM-2: an entry can never say 'constraint violated' for a constraint that was never evaluated. An auditor who reads the policy document and the audit chain side by side will find this.

**Fix.** Add an MVP story to Epic 5 (alongside Story 5.4's fail-closed matrix): the policy loader validates constraint keys against a closed, versioned vocabulary at parse time and rejects the document with a 422 naming the unknown key — a policy that cannot be fully enforced is never accepted. Implement `business_hours_only` (with a per-tenant timezone) and `dry_run` or remove them from SPEC.md and the Glossary. Move `allowed_clients` evaluation out of `gateway/server.py:247` into the shared pipeline so it applies on `/v1/authorize` too. Add a test asserting an unknown constraint key fails the document, and a test asserting each vocabulary member actually changes a verdict.

### EXH-3. The policy rule vocabulary cannot express any condition on argument *values*. A Rule binds a canonical tool name to an action class and an approval tier; the only value-aware check in the engine is an email-domain allowlist. FR-13 nonetheless promises a shipped *finance* policy template as MVP.

**Why it matters.** 'Deny transfers over EUR 10,000', 'auto-approve refunds under EUR 500, hold the rest', 'allow deletes only on records older than 90 days' is the first policy every buyer in the stated ICP tries to write, and the engine cannot express any of it. The only available expression is tool-level: hold *every* transfer. That is not graduated autonomy — it is a queue, and it manufactures exactly the two counter-metrics the PRD says matter most: CM-2 rubber-stamping (an approver who sees 200 identical holds a day stops reading the Decision Brief) and CM-1 auto-tier widening (the tenant moves the tool to `auto` to make the pain stop). Risk Bands are not a substitute: `core/risk.py` scores blast radius (fan-out count) and DLP sensitivity, not magnitude, and a band maps a score to a tier rather than expressing a business predicate. The 'finance' template in FR-13 cannot be written credibly against this vocabulary, and shipping a thin one is worse than shipping none.

**Fix.** Add an MVP FR to Group A / Epic 9 for a bounded, deterministic argument-predicate vocabulary on Rules: a small closed set of typed operators (numeric compare, string equality, set membership, regex on a named field, list-length cap) over a JSON-path-style field selector, with tier-per-branch. Keep it deliberately non-Turing-complete so NFR-1 determinism, FR-60 replay and FR-11 simulation all still hold. Fail closed when a referenced field is absent or the wrong type — never evaluate to allow. Note the §4.10 interaction explicitly: predicates read arguments in memory and must record only the rule id and matched-branch name in the audit entry, never the value. Then build the finance template on top of it, and use it as the worked example in the policy editor.

### EXH-4. Generic executor tools have no deterministic classification story. `docs/SPEC.md:198` shows the product's answer for `shell.exec`: `classify: ambiguous` — i.e. the LLM judge infers the action class from arguments. FR-6 (multilingual name stems), FR-53 (annotations as floor) and the risk score do not address it, and no FR mentions code execution, shell, kubectl, HTTP request or browser tools.

**Why it matters.** One tool name — `bash`, `run_python`, `execute_sql`, `http.request`, `kubectl` — covers read, write, external_send and irreversible simultaneously. This is not an edge case; it is the highest-blast-radius tool in nearly every production agent stack, and the canonical-tool-name policy model collapses entirely on it. The plan's fallback routes the most consequential authorization decision in the product to the LLM judge, which sits uncomfortably against NFR-1 ('no LLM call participates in any authorization decision') — for these tools the judge's class inference *is* the decision — and against G-C1/FR-34, since a code-exec-heavy agent burns the judge budget on every call and, on exhaustion, over-classifies everything to irreversible, i.e. holds every call. Neither branch is shippable. A buyer running Claude Code, Codex-style, or any DevOps agent hits this on day one, and 'we control what the agent does' does not survive 'we cannot tell what `bash` is doing'.

**Fix.** Add an MVP FR: declare an `executor` tool kind in the policy with deterministic per-tool argument-pattern classification — an ordered command/verb allowlist and denylist evaluated over the designated argument field, mapping matched patterns to action classes, with no-match failing closed to the tool's declared ceiling. Use the same predicate machinery as the fix above. Ship executor patterns in the DevOps template. Then narrow the judge to what NFR-1 actually claims for it: genuinely novel tool *names*, not per-call argument inspection on hot executor tools. If this is out of scope for v2.0, say so explicitly in §6.2 with a reason and add it to the FR-144 coverage map as an honest not-covered row — silence is the worst option, because the coverage map is a headline deliverable.

### EXH-5. v2.0 is 139 stories across 13 epics (29 L, 87 M, 48 S overall), 129 of 152 FRs tagged [MVP], with no timeline, no capacity assumption, no phasing and no cut line. Epic 13 depends on Epics 1-12 and enforces FR-110 ('a backend capability without a console surface has not shipped') as a gate over all of them.

**Why it matters.** By the document's own effort key (S = hours, M = one to two days, L = several days), v2.0 is on the order of a year of single-engineer work before review and integration. Nothing can be released until Epic 13 closes, because FR-110 makes every backend capability's console page a release condition — that is a waterfall with a single delivery point, which is the highest-risk possible shape for a plan whose central complaint about the current state is that things ship to main unverified. The PRD states a crisp one-sentence scope test ('a stranger can self-host it in ten minutes, every action and every administrative change is recorded, every decision explains itself, and an auditor can verify the record without trusting us') that is satisfied by Epics 1-4 plus the verification FRs — perhaps 60 stories. Epics 7, 8, 10, 11, 12 (agent plane, universal ingress, budgets, evidence packs, egress) are all outside that sentence and all tagged MVP. Meanwhile the market pressure described in §12 is measured in months.

**Fix.** Split the release. Declare v2.0-core = Epics 1, 2, 3, 4 and 5 — exactly the scope-test sentence — as the GA boundary, with FR-110's console gate scoped to the controls that release ships rather than to everything. Move Epics 6-13 to v2.1/v2.2 with their own dates. Add a stated capacity assumption and target date to the PRD, and add an explicit priority ordering *inside* v2.0-core so there is a defined answer to 'what falls out if we are late' other than 'everything slips'. Note that Epic 6 (Emergency Stop) is arguably the one Group-B item that belongs in core — it is a named CISO buying criterion and OP-3/C-6 depend on it — so consider promoting it and demoting something else rather than shipping all of Group B.

### EXH-6. The plan retains and hardens a full LLM cost/telemetry plane that its own §5 disclaims: FR-77 (cached-read vs cache-creation vs reasoning tokens priced distinctly, estimated versus provider-billed side by side), FR-151/152 (OTLP gen_ai attribute tracking), and the LLM provider proxy as a first-class Ingress Path that Epic 5 must unify into the pipeline (Story 5.3 touches `api/llm_proxy.py`) — while FR-5, the requirement that would let that path see streamed tool calls at all, is deferred to post-v2.0.

**Why it matters.** §5 non-goal 3 freezes observability at 'enough to decide and to explain a decision.' A provider-accurate, multi-provider, cache- and reasoning-token-aware pricing ledger reconciled against provider billing is not that — it is a FinOps product, it is given away free by LiteLLM, Helicone, Langfuse, Portkey and OpenRouter, and provider pricing changes constantly, so it is a permanent maintenance tax on a differentiator-free surface. Budgets (FR-75/76) are genuinely in-thesis because a budget *denies*; cost accounting precision is not. The proxy is worse: it sits in the request path of every model call, forces xSOM to hold customer provider credentials (DG-7 key custody), produces `cooperative` verdicts at best, is flagged by FR-89 as an active security liability today, and — with FR-5 deferred — cannot see tool calls in streamed completions, which is how essentially all production agent traffic runs. Epic 5 therefore spends real effort making a structurally blind path look consistent with the two paths that work. Every hour on this is an hour not spent on Epics 1-4, and it is the exact dilution that lets a buyer file xSOM under 'another LLM observability tool.'

**Fix.** Cut, explicitly, in §6.2 with reasons. (a) Reduce FR-77 to token counts captured and spend labelled 'estimated'; defer the pricing tables and provider-billing reconciliation. (b) Keep FR-152's standard correlation keys — session/trace/conversation ids serve lineage and UJ-4, which is in-thesis — and cut the usage/cost dashboard surface (`/v1/ai/summary`, `/v1/ai/costs`) as a shipped product area. (c) Demote the LLM provider proxy from Ingress Path to an optional non-enforcing telemetry tap, remove it from FR-1's unification scope and from Story 5.3, and say plainly in FR-144's coverage map that model-call interception is not an enforcement surface in v2.0. Also reconsider FR-112 (English/French console parity) as MVP — enterprise security tools ship English-only for years and no evaluation turns on it. Redirect the freed effort to the monitor mode and policy expressiveness gaps above.

### EXH-7. FR-131 ships five framework mappings (EU AI Act, GDPR, ISO/IEC 42001, NIST AI RMF, SOC 2) as MVP, in a release whose own §12 states that the compliance deadline moved by over a year and that the economic buyer shifted from the compliance officer to the CISO.

**Why it matters.** This is an internal contradiction. §12 and §7 are explicitly repositioned away from compliance-readiness percentages toward explainability and verification, and §2 names the CISO as the buyer — yet Group D still spends MVP budget on four additional framework mappings beyond the one (EU AI Act) already built in M9. Control mapping is not a rendering exercise despite FR-131's claim: mapping evidence onto SOC 2 CC-series or ISO 42001 Annex A controls credibly requires audit expertise, and a mapping a real assessor rejects is worse than no mapping, because it damages exactly the credibility this release exists to build. It also collides with C-1's own discipline that no framework verdict may be asserted beyond what the data supports.

**Fix.** Ship EU AI Act plus the raw hash-bearing evidence appendix, the Data Manifest, and the standalone verifier — the three artifacts an assessor for *any* framework can work from. Move ISO 42001, NIST AI RMF, SOC 2 and GDPR mappings to v2.1 in §6.2, with the reason stated: each needs review by a practising assessor before publication. Keep the declarative mapping table architecture so adding frameworks later is cheap. This is a cut that strengthens C-1 rather than weakening the compliance story.

### EXH-8. Console identity federation (FR-82, OIDC/JWKS with IdP group-to-Role mapping) is deferred out of v2.0, and SAML/SCIM are explicitly out — while §2 names the CISO/Head of AI Platform as the economic buyer, FR-79 ships an email-invite membership plane, and SM-9 targets 70% of tenants having more than one Member.

**Why it matters.** These cannot all be true at once. Enterprise security-tool procurement treats SSO as a table-stakes gate; a CISO cannot approve a tool that holds approval authority over production actions and manages its own user directory with email invites. The plan's own separation-of-duties story (FR-19), human_dual (FR-80) and the entire oversight-effectiveness claim (C-5, SM-5) all depend on real multi-member tenants, and SM-9's 70% target is unreachable if adding a member means creating a shadow identity outside the customer's IdP. Note the plan already builds most of what is needed: FR-87 makes authentication resolve through a pluggable JWKS issuer for the self-host path. FR-82 is largely the group-to-Role mapping on top of that, not a new subsystem — so the deferral buys less than it costs.

**Fix.** Promote OIDC federation (FR-82) into v2.0 as MVP, scoped narrowly to what FR-87's pluggable JWKS issuer already implies: accept a customer OIDC issuer for console login, plus a declarative IdP-group-to-Role map, plus a Control-Plane Event on role assignment. Leave SAML and SCIM deferred — that deferral is defensible; deferring OIDC entirely is not. If it genuinely cannot fit, then lower SM-9's target and state plainly in the coverage map that v2.0 targets teams willing to manage identity inside xSOM, so the mismatch is disclosed rather than discovered in a security review.

### EXH-9. The 'unoccupied intersection' positioning in §1/§12 rests on three legs — enforced human approval, verifiable evidence, tool supply-chain integrity — but the plan never confronts that the first leg is being commoditised, and its own Epic 8 concedes the point. FR-50 routes LangGraph's HIL hook, the OpenAI Agents SDK approval callback, the Claude Agent SDK pre-tool hook and CrewAI *to* xSOM; SM-10 targets 25% of supervised calls arriving that way; FR-51/Story 8.6 then honestly label those decisions `cooperative` and C-7 bars them from counting as equivalent oversight evidence.

**Why it matters.** On the non-MCP path — a quarter of target volume, and the majority of the real agent market by the PRD's own §B3 reasoning — the framework already owns the approval interrupt, and the identity vendors now bundle async human approval for agent actions with the IdP the customer already pays for. What xSOM adds there is the *record*, not the enforcement. That is a genuinely defensible product, but it is a different sentence from 'we control what the agent does', and the plan never writes that sentence down. The result is that the strongest claim (mandatory enforcement) is true only on MCP, and the honest labelling the plan rightly insists on makes that visible to every buyer at exactly the moment they are evaluating. Meanwhile §12's competitor analysis names no one — 'a hyperscaler', 'a direct competitor' — so there is no per-JTBD win/lose analysis anywhere in the document, and no test of the intersection claim against the vendors most likely to erode it.

**Fix.** Add a competitive section to the PRD with named alternatives (hyperscaler agent gateways, open-source MCP gateways, identity vendors shipping agent approval, tamper-evident ledger vendors, and the frameworks' own built-in HIL hooks) and, for each JTBD in §2.1, an explicit where-we-win / where-we-lose row. Then resolve the positioning consequence directly: state the two-tier value proposition — mandatory enforcement plus verifiable evidence on MCP, and unified policy plus verifiable evidence across frameworks on the SDK path — and make it the frame for FR-143/FR-144 rather than a single blended claim. Feed the answer into OQ-1 and OQ-12, which currently gate the release announcement and GA with no analysis behind them. Separately, give CM-3 and OP-8 actual numbers: the plan adds roughly nine guards to an inline hot path where `core/db.py:19` opens a fresh connection per operation and FR-78 pooling is deferred to Epic 14, yet the latency budget is written as 'a small, budgeted margin' and capacity guidance has no figures. An inline gateway with no published p95 overhead number will be rejected on that basis alone.
